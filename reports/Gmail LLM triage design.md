# Personal Gmail triage: build with API polling and cascades

For a single-user LLM-powered Gmail triage tool built in late 2026, the winning design is unambiguous on most axes and genuinely contested on a few: use the Gmail REST API (never IMAP), accept that reading-plus-relabeling mail requires at least one Google "restricted" OAuth scope so a CASA security review is structurally unavoidable *unless* the app stays personal-use-exempt, and lean on `history.list` polling every 1-5 minutes rather than the officially-favored push+Pub/Sub stack, since a single mailbox trivially fits inside Google's quota and polling avoids a public webhook, a Cloud Pub/Sub topic, and a weekly watch-renewal cron. Classification should be a cascade -- free header/sender heuristics first, then one temperature-0 LLM call with JSON-schema-constrained output, with a review bucket sized to what a human will actually look at daily rather than to the model's self-reported (and widely distrusted) confidence score. Taxonomy design converges on a small mutually-exclusive response-state field (To Respond / Awaiting Reply / FYI / Done) plus an orthogonal content tag and priority score, a pattern most clearly implemented by Fyxer, not Superhuman as commonly assumed. Feedback should be captured as versioned natural-language rule edits or a lightweight incremental classifier with held-out evaluation gates, not full RLHF. Safety hinges on one structural move -- never grant a send scope, and validate every LLM output against a code-enforced label allowlist -- which removes the "exfiltration" leg of the "lethal trifecta" that caused every real-world 2024-2025 prompt-injection incident found in this research. Cost is a non-issue at personal scale: even fully unoptimized, per-email classification runs about $2.60 per 1,000 emails on the priciest small model surveyed, and drops toward $0.05-0.23 per 1,000 with caching and batching on cheaper models.

## 1. Gmail API beats IMAP, but reading content always touches a restricted scope

- The Gmail REST API is the clear choice over IMAP: it exposes native label semantics (system labels like `IMPORTANT`, `CATEGORY_*`, plus user labels), incremental sync via `history.list`, push notifications, and batch-modify endpoints IMAP has no equivalent for, while IMAP's advantages (protocol universality, no Google Cloud project) don't matter for a Gmail-only tool that already needs OAuth either way ([IMAP vs Gmail API vs Graph API, Nylas](https://cli.nylas.com/guides/imap-vs-gmail-api-vs-graph-api)).
  - This comparison comes only from vendor blogs (Nylas, Unipile) -- Google publishes no primary comparison **[secondary source]**.
- Google's own scopes reference confirms `gmail.readonly`, `gmail.modify`, `gmail.compose`, `gmail.insert`, and `mail.google.com` are all **restricted** ([Gmail API OAuth scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)); `gmail.labels` is non-sensitive.
  - There is **no scope combination that both reads message content and relabels/archives without touching a restricted scope** -- `gmail.readonly`, `gmail.modify`, and `gmail.metadata` are all restricted, so scope-minimization cannot dodge the review question by itself.
  - `gmail.metadata`'s restricted classification rests only on a secondary source ([Gmail API Scopes Explained, Unipile](https://www.unipile.com/gmail-api-scopes-guide/)) -- Google's own fetched scopes page didn't itemize it directly **[unverified -- re-check against https://developers.google.com/identity/protocols/oauth2/scopes#gmail]**.
- Restricted scopes require a CASA third-party security assessment once an app exceeds 100 test users, reportedly costing "$15,000-$75,000 or more" and taking weeks to months ([GMASS blog](https://www.gmass.co/blog/google-oauth-verification-security-assessment/)).
  - Google explicitly exempts apps "used by only a few users, all of whom are known personally to you" from verification entirely ([Sensitive scope verification, Google for Developers](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)) -- exactly this project's situation.
- The real friction is the **7-day refresh-token expiry** for apps left in OAuth "Testing" publishing status.
  - Restricted scopes get no exemption from this clock: "if an application requests gmail.readonly, the 7-day expiration exception does not apply... a hard seven-day clock" ([Unipile: Google OAuth Refresh Token](https://www.unipile.com/google-oauth-refresh-token/)) **[secondary source]**.
  - The widely-corroborated workaround: flip the consent screen's publishing status to "In production" while remaining formally unverified -- "refresh tokens generally don't expire unless revoked or unused for six months" (same source) -- at the cost of a one-time "Google hasn't verified this app" warning click.
  - **No Google primary source explicitly states "In production + unverified" is a durable, sanctioned state rather than a policy gray area** **[inference / unverified]** -- build defensive re-auth handling regardless.

## 2. Sync mechanics: polling history.list beats push notifications at single-mailbox scale

- Google's push-notification guide: call `users.watch()` to register a Cloud Pub/Sub topic, after which Gmail publishes a bare (email, historyId) notification on every mailbox change ([Gmail push notifications guide](https://developers.google.com/workspace/gmail/api/guides/push), fetched Sept 2026).
  - **The watch registration expires after at most 7 days and must be renewed**: "You must call the watch method at least once every 7 days or you'll stop receiving updates" (same page).
  - `users.watch` costs 100 quota units; renewing daily is negligible against the 1,200,000 units/minute project cap ([Gmail API usage limits](https://developers.google.com/workspace/gmail/api/reference/quota)).
- Every notification must be followed by `history.list` (2 quota units) to learn what changed, using a stored historyId ([Synchronizing Clients with Gmail](https://developers.google.com/workspace/gmail/api/guides/sync)).
  - History records are "typically available for at least one week and often longer... might be significantly shorter... in rare cases" (same page).
  - A stale historyId returns HTTP 404, requiring a full resync via `messages.list`/`messages.get`. For a laptop-hosted tool that may be offline for stretches, **this should be treated as a routine, tested code path, not an edge case** **[inference]**.
- Google frames push+history as existing specifically to avoid "needless polling" (same page) -- an official preference for push -- but no primary source recommends or forbids a specific polling interval.
  - At 2 units per `history.list` call, polling every minute costs only 2,880 units/day, trivially inside the 80,000,000-unit daily threshold.
  - Push requires a public HTTPS endpoint (or pull-subscription consumer), a GCP Pub/Sub topic/subscription, IAM grants to the Gmail push service account, and weekly watch renewal.
  - **Plain polling of `history.list` every 1-5 minutes is the pragmatically simpler choice for a single-user tool** **[inference -- not a documented Google recommendation]**, trading a few minutes of latency for a meaningfully simpler operational footprint.
- Rate limits are essentially a non-concern at this scale.
  - As of a Google page updated September 10, 2026: 1,200,000 units/minute/project, 6,000 units/minute/user/project ([Gmail API usage limits](https://developers.google.com/workspace/gmail/api/reference/quota), fetched directly).
  - Per-call costs from that page: `messages.get` 20 units, `messages.list` 5 units, `history.list` 2 units, `batchModify`/`batchDelete` 50 units, `messages.send` 100 units, `users.watch` 100 units.
  - A conflicting secondary source claims `messages.get` costs only 5 units with a 250-units/second cap ([Unipile: Gmail API Limits](https://www.unipile.com/gmail-api-limits/)) -- **the directly-fetched Google page is authoritative; treat Unipile's figures as stale or wrong** **[conflict -- Google wins]**.
  - `batchModify` caps at 1,000 message IDs per call ([Method: users.messages.batchModify](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/batchModify)); a 10,000-message backlog reclassification costs roughly 10 batch calls (500 units) plus whatever read calls decided the labels -- LLM inference cost, not API quota, is the real bottleneck for bulk jobs.

## 3. Labels, filters, and native rules as a free pre-classification tier

- Gmail's native filter system (`users.settings.filters`, requiring `gmail.settings.basic` **[unverified scope requirement]**) can handle static sender/subject-based routing at zero LLM cost, reserving the model for genuine judgment calls.
  - A claimed 1,000-filter-per-account cap and the exact `batchDelete` message limit were **not independently confirmed against a primary Google page** **[unverified -- re-check]**.
- Gmail's own ML-driven `CATEGORY_*` labels (Promotions/Social/Updates/Forums/Personal) are readable via the API and worth treating as a free prior feature.
  - Removing `CATEGORY_PROMOTIONS` has the side effect of moving a message to Primary ([Manage labels, Google for Developers](https://developers.google.com/workspace/gmail/api/guides/labels)).
  - Gmail's smart categories famously "don't sync to third-party apps" reliably ([Missive Docs](https://missiveapp.com/docs/core-features/connected-accounts/email-accounts/gmail-google-workspace/using-gmail-smart-categories)) -- treat as a prior, not ground truth.

## 4. Classification: a rules-then-LLM cascade with empirical, not self-reported, confidence

- Cheapest tier -- near-free heuristics:
  - RFC 8058's List-Unsubscribe / List-Unsubscribe-Post headers, mandated by Gmail and Yahoo for bulk senders since 2024 ([RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html); [Mailgun](https://www.mailgun.com/blog/deliverability/what-is-rfc-8058/)).
  - The legacy Precedence: bulk header, sender-domain patterns.
  - A concrete open-source implementation, [dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (read via summary, not primary source **[secondary source]**), hard-codes sender-pattern rules at confidence 1.0 that bypass the LLM entirely.
- Second tier -- zero-shot LLM classification with structured output:
  - The dominant 2025-2026 pattern constrains output to a JSON schema -- "native structured output with constrained decoding... works 100% of the time with schema-valid guarantees" by masking invalid tokens at the sampler level ([dev.to: LLM Structured Output in 2026](https://dev.to/pockit_tools/llm-structured-output-in-2026-stop-parsing-json-with-regex-and-do-it-right-34pk)).
  - gmail-triage runs this "at temperature 0 with JSON-schema enforcement," finding it "works acceptably from ~4B parameters" with a 7-8B model as the practical local floor **[secondary source]**.
  - A separate hands-on test found models under 4B "hallucinated inappropriately, drafting replies to automated notifications," with a 4B model as the sweet spot on modest hardware ([Zineb Bendhiba: I Tested Local LLMs to Triage My Gmail](https://zinebbendhiba.com/posts/i-tested-local-llms-to-triage-my-gmail-here-s-what-worked/)).
- Few-shot vs. zero-shot:
  - Few-shot reliably beats zero-shot in published benchmarks but by a modest margin -- one study found accuracy of "0.320 for zero-shot... 0.363 for few-shot" ([Ruma Sinha, Medium](https://rumasinha.medium.com/text-classification-with-llm-00944c169ba0)).
  - "Marginal accuracy improvements may not justify doubling inference time" ([arXiv 2508.14170](https://arxiv.org/pdf/2508.14170)).
  - Given the cold-start problem (day-one users have zero labeled examples): **zero-shot first, switching individual categories to few-shot once corrected examples accumulate** **[inference]**.
- Fine-tuned small classifiers vs. LLM:
  - Fine-tuned small encoder models (BERT-style) still outperform zero-shot LLMs "when even a moderate amount of labeled data is available" ([arXiv 2406.08660](https://arxiv.org/abs/2406.08660)).
  - 2026 practitioner consensus favors hybrids -- "BERT handles fast, low-cost classification, and LLMs tackle reasoning and edge cases" ([Kaggle discussion](https://www.kaggle.com/discussions/questions-and-answers/715272)).
  - No source addresses whether a single user can accumulate enough labels to make fine-tuning worth the maintenance burden; **for personal scale, LLM zero/few-shot is likely sufficient, with fine-tuning deferred as a later optimization** **[inference]**.
- Embeddings + kNN:
  - Plausible and cheap -- embedding tens of thousands of short emails costs well under $1 at $0.02/1M-token pricing.
  - **No source benchmarked embeddings+kNN specifically for email classification** -- a genuine research gap.
- Confidence thresholds and abstention:
  - Strong convergence that self-reported LLM confidence is not trustworthy for gating decisions: "a fluent answer or a self-reported confidence score does not settle that question" -- thresholds must be calibrated against held-out labeled data ([vdf.ai](https://vdf.ai/blog/local-model-router-calibration-escalation-abstention/)).
  - "Review capacity" (how many emails a day the user will actually check) should be a hard constraint on the abstention threshold, not an afterthought (same source).
  - Cascade-routing literature agrees: "LLM confidence scores, including raw token entropy and token margins, are typically miscalibrated" ([arXiv: Dynamic Model Routing and Cascading Survey](https://arxiv.org/pdf/2603.04445)).
  - Practical proxy: log every classification alongside the user's eventual correction, and periodically compute **empirical per-category precision** rather than trusting the model's own number -- the gmail-triage pattern **[secondary source, but pattern corroborated across multiple independent sources]**.

## 5. Taxonomy: a response-state field plus an orthogonal priority score

- Fyxer's default taxonomy: "To Respond, FYI, Action, Comment, Notifications, Meeting Updates, Awaiting Reply, and Marketing," with "Awaiting Reply" as an explicit state transition after replying to a "To Respond" item ([Fyxer](https://www.fyxer.com/blog/how-fyxer-organizes-your-inbox-by-priority)).
  - **This response-lifecycle scheme is most directly attributable to Fyxer, correcting a common assumption that Superhuman popularized it.** Superhuman instead provides "a lighter layer of AI... uses split inboxes... with more control over categorized emails because you create the categories yourself" -- user-defined folders, not a fixed automatic taxonomy ([Jotform: Fyxer AI vs Superhuman](https://www.jotform.com/ai/agents/fyxer-ai-vs-superhuman/)).
  - **Front's specific taxonomy was not evaluated in this research, and no source corroborated an "Eisenhower matrix" framing for email triage specifically** -- both should be treated as unconfirmed if referenced elsewhere.
- A distinct content/urgency taxonomy: URGENT, ACTION_REQUIRED, INFORMATIONAL, SUSPICIOUS, PURCHASE, SHIPPING -- deliberately splitting commerce mail and adding a SUSPICIOUS bucket distinct from Gmail's own spam handling ([Zineb Bendhiba](https://zinebbendhiba.com/posts/i-tested-local-llms-to-triage-my-gmail-here-s-what-worked/)).
- Gmail's own built-in categories are "mutually exclusive, ML-classified, and cannot be customized" ([usecarly.com](https://www.usecarly.com/blog/how-to-categorize-emails-in-gmail/)).
- Priority/urgency is generally a separate scoring layer, not folded into the category set.
  - One source describes a 1-5 importance scale plus coarse buckets like "Act Now / Read Promptly / Act or Read Later / Other" -- traces to a patent filing, not an engineering source **[weak/indirect evidence]** ([USPTO filing](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9152953)).
- Synthesis: a personal tool likely needs **a small mutually-exclusive response-state field (To Respond / Awaiting Reply / FYI / Done), a multi-label content-type tag, and a separate priority score** rather than one flat category list **[inference -- no single source states this combined design]**.
  - Category counts cluster around 5-8 across examples (Fyxer: 8; Zineb Bendhiba: 6) -- no source states an explicit optimal-count principle **[inference from pattern-matching]**.
  - MailTriage lets users author categories as plain-language criteria text where that text *is* the LLM prompt -- a practical way to make the taxonomy user-editable without code changes.

## 6. Feedback loops favor versioned rules over full retraining

- Three concrete mechanisms found at personal scale -- no example of RLHF-style reward-model retraining was found at this scale:
  - **Lightest**: a plain corrections file appended as few-shot examples -- a published Claude Code "Email Triage" skill describes "a corrections log for few-shot learning" ([mcpmarket listing](https://mcpmarket.com/tools/skills/email-triage)) **[secondary source]**.
  - **Middle**: MailTriage/gmail-triage treats a correction as a diff to the category's plain-language criteria -- "the system proposes a criteria revision shown as a diff... approval bumps the category's criteria version (full history with restore)" ([dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage)) -- a correction edits the rule text that *is* the classifier, not weights or a few-shot pool.
  - **Heaviest**: [InboxLearn](https://github.com/sohaib-0897/InboxLearn) retrains an incremental linear classifier over a hashed bag-of-words feature space from accumulated corrections as "immutable feedback records," gating any new model behind "before/after prediction comparison and held-out evaluation... required before activation." This candidate-model-plus-held-out-eval pattern is reusable for any correction mechanism, not just statistical ones **[inference]**.
- Per-sender memory is a lookup table, not free-text rules, in shipped products:
  - SaneBox keys training on **(sender, subject-pattern) pairs** -- different email types from the same vendor can be trained into different folders independently ([SaneBox Help](https://www.sanebox.com/help/186-how-does-sanebox-determine-trainings)) -- and reads only headers/subject, never full body content, for privacy ([SaneBox Help: How does SaneBox work?](https://www.sanebox.com/help/155-how-does-sanebox-work)).
  - Gmail's importance-ranking signals are similarly per-sender-reputation-based, factoring "what emails you mark, star, archive, or delete... which automatically marked emails you unmark" ([MakeUseOf](https://www.makeuseof.com/what-is-gmail-importance-marker/)) **[secondary source -- the primary Google Priority Inbox research paper could not be extracted as readable text in this research pass]**.
  - A directly reusable design: maintain a small per-sender key-value store checked *before* invoking the LLM, so repeat senders short-circuit to a cheap deterministic answer **[inference]**.
- Natural-language preference rules span two poles:
  - MailTriage's raw prompt-injection of user criteria text vs. a general (non-email) technique called "Compile by Training" that compiles a spec into a reusable, cheaper, deterministic program ([arXiv 2609.04199](https://arxiv.org/pdf/2609.04199)).
  - Shortwave's public docs are explicitly undisclosed about which end they use **[unverified -- proprietary]**.
  - A practical middle ground: parse a natural-language preference into a structured rule object but keep the original sentence attached as its audit trail **[inference]**.
- Evals and golden sets:
  - [Loukas998/email_triage](https://github.com/Loukas998/email_triage) is the clearest personal-scale example: a hand-labeled 16-case golden set, scored with a lenient "exact / acceptable / missed" verdict, gating that "no easy cases are missed."
  - General (non-email) golden-dataset guidance recommends sourcing from real production traffic, with "20 to 50 reviewed items" as a minimum viable set, growing to "100 to 1000" for a full regression suite ([Langfuse](https://langfuse.com/resources/engineering/golden-dataset-evaluation)).
  - **No source describes building a golden set from a user's own historical archive/star/read behavior as ground truth** -- every example uses hand-written or synthetic labels; this is a genuine gap and a design idea worth flagging as unvalidated (archiving something right after reading it doesn't reliably mean "unimportant") **[inference -- novel, unvalidated]**.

## 7. Products converge on draft-only automation, split between live intervention and digest review

- **Draft-only, never auto-send** is the dominant safety convention across every product surveyed except one:
  - A hobby project (inbox-agent) states plainly "There is no SMTP code, no send, no API that transmits mail," using read-only IMAP with scoped app passwords ([AleBrito124356/inbox-agent](https://github.com/AleBrito124356/inbox-agent)).
  - Cloudflare's official [agentic-inbox](https://github.com/cloudflare/agentic-inbox) is the outlier, exposing a *send* tool to the agent -- a materially higher-trust permission model than everything else surveyed.
- **Auto-archive as a named pattern**: Superhuman's "Auto Archive... clears low-priority mail" ([search-aggregated Superhuman review summary](https://efficient.app/apps/superhuman)) and Inbox Zero's "Bulk Archiver" plus "Cold Email Blocker" (auto-blocks cold emails) ([GitHub: elie222/inbox-zero](https://github.com/elie222/inbox-zero)) are both explicit auto-archive implementations, distinct from drafting.
- **Live intervention vs. asynchronous digest is a real design fork**, and products split cleanly on it:
  - Live/continuous: [Inbox Zero](https://github.com/elie222/inbox-zero) runs "AI Rules" that "run automatically after they are enabled" ([Inbox Zero security docs](https://docs.getinboxzero.com/essentials/security-and-data)); Superhuman's Split Inbox, Auto Archive, and Instant Reply all operate on the live inbox view with no digest feature found ([superhuman.com/mail](https://superhuman.com/mail)); Shortwave's "inbox already sorted" framing suggests background/live processing, not a scheduled outbound email **[inference -- not explicitly confirmed as push vs. batch]**.
  - Asynchronous/digest: **SaneBox** moves low-priority messages to a "SaneLater" folder and sends a **Daily Digest** summarizing what was filtered so nothing is missed outright ([SaneBox Help: How does SaneBox work?](https://www.sanebox.com/help/155-how-does-sanebox-work)) -- filtered mail is moved and batched for periodic human review, not hidden or deleted. The small hobby project inbox-agent generates a markdown daily digest (urgent / action-items / awaiting-reply-3-days+) rather than touching the inbox live ([AleBrito124356/inbox-agent](https://github.com/AleBrito124356/inbox-agent)).
  - For a personal tool, the digest pattern (SaneBox-style) trades immediacy for a lower-anxiety, bounded daily review surface -- a legitimate alternative to live auto-labeling, particularly paired with the abstention/review-bucket design from section 4 **[inference]**.
- SaneBox is explicitly metadata-only: it "does not analyze full email body content; classification is based on headers (sender, subject, etc.) and behavioral/interaction signals" (same source) -- a deliberately lightweight, non-LLM-driven classifier, distinct from every LLM-based product surveyed.
- Other product notes:
  - Fyxer's default taxonomy ("to respond / notification / fyi") is coarser than customizable competitors; vendor claims like "trained on 500,000+ hours of executive expertise" and "cuts 80% of inbox noise" carry no disclosed methodology **[vendor claim -- unverifiable]** ([fyxer.com/for-ai-assistants](https://www.fyxer.com/for-ai-assistants)).
  - Superhuman markets the most aggressive automation stance surveyed -- drafting, and if opted in, sending fully written emails on the user's behalf ([superhuman.com/mail](https://superhuman.com/mail)) -- as explicit opt-in, but almost no technical/permission detail is public; most feature specifics trace to third-party review aggregators **[secondary source]**.
  - Shortwave's clearest documented mechanism is an explicit "apply to future messages" per-sender auto-label rule ([Shortwave Docs](https://www.shortwave.com/docs/how-tos/manage-auto-apply-labels/)); its 2023 engineering blog describes running many parallel calls to a fast LLM, with each call optimized to extract one specific feature -- a reusable modularity pattern, though the post **predates the 2025-2026 rebuild and should be treated as stale** ([Shortwave Blog, 2023](https://www.shortwave.com/blog/deep-dive-into-worlds-smartest-email-ai/)) **[freshness flag]**.
  - Inbox Zero's docs don't disclose the underlying LLM provider or exact OAuth scope strings for the main hosted app **[gap]**; a companion CLI/agent-skill variant reportedly splits read-only vs. write scopes, but that's unverified for the main app **[unverified -- secondary source]**.
  - As of a January 8, 2026 Google blog post, Gmail's shipped GA AI centers on drafting/summarizing (Help Me Write, AI Overviews, Suggested Replies); a more agentic "AI Inbox" is explicitly **beta/limited rollout**, and a "Gemini Inbox" (needs-follow-up/done/ready-for-review) spotted in test builds as of July 2026 is **not yet available to anyone** ([Google Blog](https://blog.google/products-and-platforms/products/gmail/gmail-is-entering-the-gemini-era/); [TestingCatalog](https://www.testingcatalog.com/google-tests-new-gemini-inbox-section-for-workspace-triage/)).
  - Fastmail takes the opposite architectural bet: "zero built-in AI, by design" **[unverified -- traced to a secondary aggregator, not Fastmail's own blog]** ([AlternativeTo](https://alternativeto.net/news/2026/4/fastmail-launches-mcp-server-to-enable-direct-ai-integration/)), instead shipping an MCP server so users connect their own AI client under their own authorization ([Fastmail Blog](https://www.fastmail.com/blog/an-mcp-server-for-fastmail/)) -- filtering stays on Sieve (RFC 5228). This validates the core premise of building a personal external triage agent rather than waiting for a vendor to ship one.

## 8. Safety: untrusted email content demands capability limits, not just prompt fencing

- Documented, real-world prompt-injection incidents against production LLM agents (not theoretical):
  - **CVE-2024-5184** (EmailGPT, CVSS 9.1) let attackers override system prompts via unsanitized email content ([Black Duck advisory](https://www.blackduck.com/blog/cyrc-advisory-prompt-injection-emailgpt.html)).
  - **EchoLeak** (CVE-2025-32711, CVSS 9.3) was a zero-click exploit against Microsoft 365 Copilot: a single crafted email exfiltrated internal file contents with no user interaction ([Sentra](https://sentra.io/blog/copilot-echoleak-prompt-injection); [arXiv 2509.10540](https://arxiv.org/abs/2509.10540)).
  - **ShadowLeak** exploited ChatGPT's Gmail-connected Deep Research agent via invisible white-on-white HTML text, exfiltrating data server-side with no trace at the victim's network boundary ([The Hacker News](https://thehackernews.com/2025/09/shadowleak-zero-click-flaw-leaks-gmail.html)).
  - A Gemini-in-Gmail flaw caused "Summarize this email" to append a fabricated phishing alert from hidden instructions ([0din.ai](https://0din.ai/blog/phishing-for-gemini)).
  - OWASP ranks **prompt injection as the #1 LLM risk** for the second consecutive edition, citing email explicitly as a vector ([Mend.io OWASP guide](https://www.mend.io/blog/2025-owasp-top-10-for-llm-applications-a-quick-guide/)).
- Every incident required an outbound/exfiltration channel to cause harm:
  - Simon Willison's "lethal trifecta": an agent with (1) access to private data, (2) exposure to untrusted content, and (3) an exfiltration vector will eventually be exploited; Meta's "Rule of Two" says an unsupervised agent may satisfy at most two of the three ([Simon Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).
  - **A personal Gmail triage agent that only reads and labels -- no send, no reply, no arbitrary URL fetch -- removes leg (3) almost entirely**, the single highest-leverage mitigation available **[inference, but strongly supported by the incident pattern]**.
- Recommended practice:
  - Fence untrusted content explicitly in the prompt: tell the model that email text is untrusted data and instructions inside it must never be followed ([Nylas prompt-injection guide](https://developer.nylas.com/docs/cookbook/agents/prevent-prompt-injection/)).
  - Grant the minimum tool surface -- Nylas: roughly 80 percent of useful email-agent work needs no send capability (same source).
  - **Enforce outputs via a deterministic, code-side allowlist rather than trusting the model's tool calls** -- unlisted tools should not exist in the system at all, regardless of what the prompt says ([The Neural Base](https://theneuralbase.com/agent-patterns/learn/advanced/tool-allowlists/)).
  - Google's own layered Gemini defense still requires mandatory human confirmation before potentially harmful actions as a backstop even with ML classifiers in place ([Google Workspace](https://knowledge.workspace.google.com/admin/security/indirect-prompt-injections-and-googles-layered-defense-strategy-for-gemini)) -- no mitigation found claims to be sufficient on its own.
  - For this project: **outputting only a label from a small, pre-declared set, validated in code, is a fundamentally lower-risk surface than free-form text generation** -- treat it as the primary control, with prompt-level fencing as defense-in-depth only.
- Least-privilege scoping:
  - Tightest defensible combination for classify-and-label: `gmail.readonly` + `gmail.labels`, adding `gmail.modify` only if attaching labels in a single call is required.
  - Sources describe the `gmail.modify`/`gmail.labels` boundary inconsistently, and a Google developer forum thread confirms this is a live point of confusion ([discuss.google.dev thread](https://discuss.google.dev/t/the-scope-gmail-modify-does-not-seem-to-apply-to-labels/249108)) **[unverified -- re-check at implementation time]**.
  - `gmail.send` and `mail.google.com` should never be requested -- the task never composes outbound mail, so requesting send would violate least privilege for no functional gain.
- Data handling and retention:
  - All three major API providers (Anthropic, Google, OpenAI) state they do not train on **paid** API data by default, retaining raw inputs/outputs only for a short abuse-monitoring window.
  - Anthropic's standard retention is 30 days ([Claude Platform Docs](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)); OpenAI's is likewise 30 days ([OpenAI: Data controls](https://platform.openai.com/docs/guides/your-data)).
  - Google's **free** AI Studio tier *does* use submitted content to improve products -- a personal tool must use the paid/billed tier specifically to get the "not used for training" commitment ([Google AI for Developers: Data logging and sharing](https://ai.google.dev/gemini-api/docs/logs-policy)).
  - GDPR's household-activity exemption (Recital 18) protects the individual user running a personal tool but explicitly does **not** extend to the third-party processor providing the means for that processing -- it protects the user, not the third-party LLM API the mail is routed through ([gdpr-info.eu Recital 18](https://gdpr-info.eu/recitals/no-18/)).
  - Correspondents emailing the user are potential EU data subjects whose content is nonetheless routed through a third-party API; the pragmatic mitigation is data minimization -- log classification decisions plus a message ID/hash, not full bodies, and avoid persisting raw content longer than the retention windows above **[inference, standard privacy-engineering practice, not independently sourced]**.

## 9. Cost: negligible at personal scale; truncation and caching matter more for latency than dollars

- Current small-model pricing (fetched September 26, 2026):
  - **Claude Haiku 4.5**: $1.00/$5.00 per million input/output tokens; prompt-cache reads at $0.10/MTok but a **4,096-token minimum cacheable prompt size** -- higher than Sonnet's 1,024 or Opus's 512 ([Claude Platform Docs: Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).
  - **Gemini 3.5 Flash-Lite**: $0.30/$2.50; newer **Gemini 3.8 Flash** at promotional $0.75/$3.75 through December 31, 2026, after which prices roughly double ([ai.google.dev/gemini-api/docs/pricing](https://ai.google.dev/gemini-api/docs/pricing)).

  - One secondary aggregator claimed GPT-5 mini at $0.125/$1.00 as of July 2026 -- **the directly-fetched official OpenAI page ($0.25/$2.00) is treated as authoritative; the discrepancy is unresolved and should be re-checked** **[conflict -- official page wins, but re-verify]**.
- Modeled per-email classification call (roughly 2,000-token fixed system prompt/taxonomy + roughly 400 tokens of truncated email content + roughly 40 tokens of structured output), per 1,000 emails:
  - Unoptimized: **$2.60** (Haiku 4.5) down to **$0.14** (GPT-5 nano).
  - With caching: roughly **$0.23 per 1,000** (GPT-5 mini) and **$0.05 per 1,000** (GPT-5 nano); stacking the roughly 50% batch discount roughly halves those again.

- At **20 emails/day** (the notes' modeled assumption), worst-case unoptimized cost is roughly **$1.56/month**; at a heavier few-hundred-emails/day volume, unoptimized cost scales roughly proportionally to **$15-25/month** -- still negligible relative to model-quality tradeoffs, but worth stating the volume assumption explicitly rather than treating $1.56 as a universal ceiling.
  - **Model choice should be driven by classification quality, not price**, once basic truncation is applied.
- Truncation strategies:
  - Purpose-built reply-parser libraries strip quoted chains by detecting boundaries like a "On [date], X wrote:" line, across roughly 10 locales ([govflow/email-reply-parser](https://github.com/govflow/email-reply-parser)).
  - English-only parsers are a documented failure mode for non-English quote headers -- a GitHub issue cites a Danish quote-header variant going unmatched ([twentyhq/twenty #25315](https://github.com/twentyhq/twenty/issues/25315)); a length-based fallback should catch missed locales gracefully.
  - HTML-to-text conversion and tracking-pixel/footer stripping are standard practice but **not independently sourced in this research** -- treat as engineering common sense, not a researched claim **[gap]**.
  - For a first-pass triage decision, sending only subject + sender + first paragraph is likely sufficient, though no source quantified the token-savings percentage of any specific truncation technique **[gap]**.
- Caching and batching:
  - All three providers now offer roughly 90%-off cached input and roughly 50%-off batch processing, making the caching/batching *decision* matter more than which provider implements it better -- except for Anthropic's per-model cache-floor caveat above.
  - Batch APIs (Anthropic Message Batches, OpenAI Batch, Gemini batch mode) fit nightly reclassification or one-time historical backfill well, but not live "email just arrived" triage.

## Conclusion

The most consequential design decision this research surfaces is not modeling or taxonomy -- it's that **operational simplicity (polling, "In production" publishing status, draft-only/no-send) dominates over the officially-recommended-but-heavier patterns (push+Pub/Sub, staying in Testing, agentic auto-send) at single-user scale**, because every efficiency argument for the heavier pattern assumes a multi-tenant or enterprise workload this project doesn't have. The second consequential finding is that the safety story and the cost story point the same direction: a labels-only, no-send agent is both the cheapest architecture to run and the one that structurally defeats the exact exploitation pattern (an exfiltration channel plus untrusted content) behind every documented 2024-2025 prompt-injection incident. Where the research is genuinely thin -- embeddings+kNN benchmarked against LLM classification for email specifically, personal-history-derived golden sets, and the real-world reliability of natural-language preference compilation -- those gaps should be treated as open implementation questions to validate empirically against your own inbox, not as settled practice to build on faith.
