# LLM/ML Classification Approaches and Taxonomy Design for Personal Email Triage

Research date: 2026-09-26. Scope: practical patterns for classifying/triaging email in a single-user Gmail tool, mixing rule-based heuristics, embeddings, and LLMs, plus a survey of taxonomies used by real triage products.

## Rules/heuristics for cheap pre-filtering before invoking an LLM

### Takeaway
A well-established set of near-zero-cost signals -- the `List-Unsubscribe`/`List-Unsubscribe-Post` headers (RFC 8058), the legacy `Precedence: bulk`/`list` header, sender/domain patterns, and Gmail's own ML-driven `CATEGORY_*` labels -- can classify or pre-sort a large fraction of bulk/automated mail before any LLM call, but Gmail's smart categories are not reliably accessible to third-party tools in the way a developer might hope, and the header-based signals are indicative rather than authoritative.

### Cited Findings
- RFC 8058 defines the one-click unsubscribe mechanism; since 2024 Gmail and Yahoo require bulk-mail senders to include both an `https` `List-Unsubscribe` URI and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and to honor unsubscribe requests within two days -- [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html); [Mailgun: What is RFC 8058?](https://www.mailgun.com/blog/deliverability/what-is-rfc-8058/)
- The presence of a compliant `List-Unsubscribe` pair is a strong, standardized signal that a message is bulk/marketing mail, because Google and Yahoo now mandate it for that mail class -- [Mailgun](https://www.mailgun.com/blog/deliverability/what-is-rfc-8058/)
- `Precedence: bulk` is a legacy header originally meant to prevent mail loops/auto-replies (e.g., stopping out-of-office auto-responders from replying to list mail); it is "not a spam filter trigger or deliverability metric" per se, but it still influences how some inbox software categorizes/prioritizes messages and remains present on many list/bulk sends in 2026 -- [MailTester: Precedence Bulk Header Purpose](https://mailtester.com/blog/precedence-bulk-header-purpose-modern-relevance/)
- Gmail's system labels include `CATEGORY_PERSONAL`, `CATEGORY_SOCIAL`, `CATEGORY_UPDATES`, `CATEGORY_FORUMS`, and `CATEGORY_PROMOTIONS`, corresponding to the inbox tabs; these are built-in system labels that cannot be created, deleted, or renamed via the API, though they can be manually added/removed on a message -- [Google Developers: Gmail API labels guide](https://developers.google.com/workspace/gmail/api/guides/labels?hl=en)
- Removing `CATEGORY_PROMOTIONS` from a message via the API moves it to Primary -- a side effect that "surprises developers who expected a simple label removal," per a developer-facing Gmail labels guide -- [Nylas: Gmail Labels API](https://cli.nylas.com/guides/gmail-labels-api)
- Missive's own documentation states plainly that Gmail's smart categories "don't sync to third-party apps like Missive" -- their workaround is to have the user create Gmail filters that move categorized mail into custom labels, which do sync -- [Missive Docs: Using Gmail smart categories](https://missiveapp.com/docs/core-features/connected-accounts/email-accounts/gmail-google-workspace/using-gmail-smart-categories)
- SaneBox's classification approach (a commercial personal-triage product) is explicitly described as heuristic + behavioral, not primarily LLM-based: it inspects headers (sender, subject, etc.) plus long-run user behavior (opens/replies to a sender) to decide Inbox vs. a lower-priority folder, and it is retrained by the user dragging messages between folders -- [SaneBox Help: How does SaneBox work?](https://www.sanebox.com/help/155-how-does-sanebox-work)
- A concrete open-source implementation (MailTriage/gmail-triage) treats a "sender-pattern rule with no category" as a hard rule: it classifies deterministically with confidence 1.0 and bypasses the LLM entirely, and lets the operator configure which Gmail inbox tabs (Promotions/Social/Updates/Forums) are even polled for LLM classification -- [GitHub: dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (read via WebFetch summary, not primary source text -- see Gaps)

### Inferences
- Because Gmail's `CATEGORY_*` labels are ML-generated by Google using signals a third party can't fully replicate (and Google doesn't document the model), a personal triage tool should read them opportunistically (they're accessible via `messages.list`/`messages.get` label IDs) as a cheap prior/feature, but should not rely on them as ground truth, and should expect that removing them has side effects on tab placement.
- SPF/DKIM/DMARC results were not directly documented in retrieved sources for this task; based on general email-security knowledge, these results are exposed to Gmail-side filtering but are not straightforwardly exposed to end users via the Gmail API without parsing the raw `Authentication-Results` header -- treat this as inference, not a verified finding (see Gap below).
- "No-reply" sender address patterns, sender domain allow/deny lists, and known-sender history (has the user emailed this address before) are widely used heuristics in the reviewed products (SaneBox's behavioral learning, Fyxer's "sender history") but no source gave a precise algorithm for combining them -- likely proprietary.

### Gaps
- No primary/technical source was retrieved specifically documenting SPF/DKIM/DMARC result exposure via the Gmail API (vs. raw header parsing) -- this needs direct verification against Google's Gmail API reference docs.
- The gmail-triage GitHub repo's README could not be read verbatim (retrieved via an AI-summarized WebFetch rather than raw markdown); treat the "confidence 1.0 hard rule" and "poll scope" details as reported-by-summary rather than directly quoted.
- No source quantified what fraction of a typical personal inbox these heuristics can classify before needing an LLM (e.g., "X% of mail has List-Unsubscribe").

## Zero-shot LLM classification with structured output

### Takeaway
The dominant 2025-2026 pattern is to constrain LLM output to a JSON Schema (via provider-native structured-output/JSON-mode features, Pydantic validation, or constrained/grammar-based decoding) rather than parsing free text, because native structured output with constrained decoding "works 100% of the time with schema-valid guarantees" by masking invalid tokens at the sampler level; multi-label classification is handled by allowing an array field in the schema, and confidence is typically emitted as a same-call score field even though such self-reported scores are widely distrusted.

### Cited Findings
- "Using Pydantic ensures correctness and prevents hallucinations by forcing LLMs to return valid JSON schemas," illustrated with a deterministic spam classifier example that can only emit "spam" or "genuine", never a hallucinated category -- [Medium: Building an LLM-Powered Email Classifier with LangGraph, Outlines, and Pydantic](https://medium.com/data-science-collective/building-an-llm-powered-email-classifier-and-responder-with-langgraph-outlines-and-pydantic-f1c2580c1e47)
- "Native structured output with constrained decoding using JSON Schema works 100% of the time with schema-valid guarantees, using finite state machines to mask invalid tokens" -- [dev.to: LLM Structured Output in 2026](https://dev.to/pockit_tools/llm-structured-output-in-2026-stop-parsing-json-with-regex-and-do-it-right-34pk)
- "The key is combining a schema definition, an example, and strict formatting rules in your prompt" -- [Anyscale Docs: Configure structured output for LLMs](https://docs.anyscale.com/llm/serving/structured-output)
- In the concrete MailTriage/gmail-triage implementation, classification is run "at temperature 0 with JSON-schema enforcement," and this "works acceptably from ~4B parameters," with a 7-8B instruct model (Qwen-class) recommended as the practical floor for a local model -- [GitHub: dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (via WebFetch summary)
- A personal-project test of local LLMs for Gmail triage found that models under 4B parameters "hallucinated inappropriately, drafting replies to automated notifications and bot-generated emails," while "thinking mode" (reasoning traces) added latency without improving triage accuracy on constrained hardware, and a 4B "direct answer" model (Gemma3:4B) was the practical sweet spot on a 16GB M2 Pro -- [Zineb Bendhiba: I Tested Local LLMs to Triage My Gmail](https://zinebbendhiba.com/posts/i-tested-local-llms-to-triage-my-gmail-here-s-what-worked/)
- That same taxonomy used six labels: URGENT, ACTION_REQUIRED, INFORMATIONAL, SUSPICIOUS, PURCHASE, SHIPPING -- and the model had to learn the subtle distinction between "this email has action items" (e.g., a GitHub PR notification) vs. "this email expects a reply from me," a distinction smaller models confused -- [Zineb Bendhiba](https://zinebbendhiba.com/posts/i-tested-local-llms-to-triage-my-gmail-here-s-what-worked/)

### Inferences
- For a personal Gmail tool, single-label vs. multi-label is a schema design choice, not a modeling one: a fixed enum field forces single-label; an array-of-enum field allows multi-label. The MailTriage pattern of using free-text "plain-language criteria" as the category definition (the category description text literally is the LLM prompt fragment) is a practical way to let a non-ML end user define/edit categories without touching code.
- Confidence fields returned inline by the LLM (e.g., a `confidence: 0.0-1.0` field in the JSON schema) should be treated as unreliable for thresholding decisions (see Confidence/Abstention section below) -- several sources converge on this independently.

### Gaps
- No source gave a worked example of the exact JSON Schema/tool-calling shape used specifically for multi-label email classification (e.g., an email that is both "newsletter" and "action-required").
- No head-to-head data comparing Anthropic tool-use/structured-output vs. OpenAI JSON mode vs. Google's structured output specifically for email classification accuracy was retrieved (out of scope for this pass; likely covered by a "products" research stream instead).

## Few-shot classification using the user's own labeled examples

### Takeaway
Few-shot prompting reliably outperforms zero-shot for structured classification tasks in published comparisons, but the accuracy gain is often modest (single-digit points) relative to the added token/latency cost, and no source addressed the email-specific question of how many examples or how they should be selected (fixed set vs. nearest-neighbor) in concrete, tested detail -- this is a notable gap for the personal-taxonomy use case.

### Cited Findings
- "Few-shot prompting generally outperforms zero-shot, especially for classification and structured-output tasks, while incurring substantially increased inference overhead in terms of token cost, latency, and compute usage. However, marginal accuracy improvements may not justify doubling inference time." -- [arXiv: Comparing energy consumption and accuracy in text classification inference](https://arxiv.org/pdf/2508.14170)
- In one classification study, "overall classification accuracy was 0.320 (95% CI: 0.309-0.331) for zero-shot prompting and 0.363 (95% CI: 0.352-0.374) for few-shot prompting" -- roughly a 4-point absolute improvement -- [Medium: Text classification with LLM (Ruma Sinha)](https://rumasinha.medium.com/text-classification-with-llm-00944c169ba0)
- Task-dependence: "while few-shot fine-tuning is not useful for sentiment classification, there is a >5% improvement over zero-shot GPT-4 for two tasks (TAXI1500 and SCENARIO) and similar performance for INTENT datasets" -- implying the benefit of few-shot/example-based approaches is highly task-shape-dependent, and idiosyncratic personal taxonomies (closer to "intent" classification than sentiment) are plausibly in the group that benefits -- [Dataiku Developer Guide: Comparing zero-shot and few-shot learning](https://developer.dataiku.com/12/tutorials/machine-learning/genai/nlp/byom-few-shot/index.html)
- "Zero-shot methods remain a viable, computationally efficient choice for text classification, particularly under resource constraints or when labeled data is scarce" -- i.e., few-shot's advantage specifically requires the user to already have labeled examples, which is the exact bootstrapping problem a new personal triage tool faces on day one -- [Analytics Vidhya: Mastering Zero-Shot and Few-Shot with SCIKIT-LLM](https://www.analyticsvidhya.com/blog/2025/01/scikit-llm/)

### Inferences
- Given the cold-start problem (a new user has zero labeled examples), a practical design is zero-shot-first with a fixed generic taxonomy, then switch individual categories to few-shot once the user has corrected/confirmed enough examples in that category -- this is inference, not sourced from any single article.
- Nearest-neighbor example selection (picking the k most similar labeled past emails to inject as few-shot examples, rather than a fixed static set) is the natural pairing with an embeddings/kNN store (see next section) -- no source directly tested this combination for email, but it is the standard RAG-style few-shot pattern used broadly in retrieval literature.

### Gaps
- No source specified an optimal or commonly-used number of few-shot examples (e.g., 3 vs. 10 vs. 20) for personal/idiosyncratic taxonomies specifically.
- No source directly compared "fixed few-shot set" vs. "nearest-neighbor-selected few-shot" for email or any closely analogous personal-classification task. This should be flagged to the report writer as an open question, possibly worth a follow-up search pass focused specifically on "dynamic few-shot example selection retrieval."

### Takeaway
General embedding-model guidance from 2026 (E5, BGE, Mistral Embed as open-weight contenders; OpenAI's text-embedding-3-small as a cheap, adequate default) transfers reasonably to email, but no source specifically benchmarked embedding models on email or discussed vector-store choice at personal scale (hundreds-tens of thousands of messages) -- this entire sub-question is under-covered by available sources and should be treated as a gap requiring either a dedicated follow-up search or the report writer's own reasoning.

### Inferences
- At personal scale (hundreds to tens of thousands of emails), a full vector database (Pinecone/Weaviate/Qdrant server) is almost certainly overkill; an embedded/local vector index (e.g., SQLite with a vector extension, or a flat numpy/FAISS in-process index) is the pragmatic choice -- this is the assistant's own reasoning/inference, not sourced from retrieved material, since no source directly addressed vector-store choice at this scale.
- Cost-wise, embedding tens of thousands of short emails with a $0.02/1M-token-class model is trivially cheap (well under $1 total for most personal mailboxes), suggesting cost is not a meaningful constraint on using embeddings+kNN as a pre-filter or feature source ahead of/alongside LLM classification -- inference based on the pricing figure above, not independently verified against email-length token counts.

### Gaps
- No source benchmarked embedding-based kNN classification accuracy against LLM zero/few-shot classification specifically for email or a closely analogous personal-document-triage task. This is a significant gap relative to the assigned key question and should be flagged clearly to the report writer.

## Small fine-tuned classifiers (BERT-style) vs. LLM zero/few-shot

### Takeaway
The technical literature is fairly clear that fine-tuned small encoder models (BERT-style) still outperform zero-shot LLMs when even a moderate amount of labeled data is available, and the emerging 2026 consensus among practitioners is a hybrid system (fast/cheap BERT-style classifier for the bulk of traffic, LLM reserved for reasoning/edge cases) rather than an outright replacement -- but for a personal-scale project, the practical overhead of training/maintaining a fine-tuned model is a real cost that none of the retrieved sources directly weighed against LLM few-shot for a single user's mailbox.

### Cited Findings
- "Fine-tuning smaller BERT-style models significantly outperforms generative AI models such as ChatGPT and Claude Opus (used in a 'zero-shot' fashion) across all four applications when moderate amounts of training data for fine-tuning are provided. Fine-tuning with application-specific training data achieves superior performance in all cases [except sentiment]." -- [arXiv 2406.08660: Fine-Tuned 'Small' LLMs (Still) Significantly Outperform Zero-Shot Generative AI Models in Text Classification](https://arxiv.org/abs/2406.08660)
- Nuance: "For sentiment classification, zero-shot classification with LLMs is a better option than task specific fine-tuning. In all other cases, few-shot fine-tuning achieves better performance than zero-shot classification." -- [arXiv 2406.08660](https://arxiv.org/abs/2406.08660)
- "2026 is shifting the conversation from model capability to system design. Instead of replacing BERT with LLMs everywhere, we're seeing architectures where: BERT handles fast, low-cost classification, and LLMs tackle reasoning and edge cases." -- [Kaggle discussion: Is Fine-tuning BERT Still Worth It in 2026, or Should We Just Use LLMs?](https://www.kaggle.com/discussions/questions-and-answers/715272)
- "For standard classification with decent training data, the fine-tuned encoders still dominate. To make this more accessible, users can select and fine-tune BERT-like LLMs for any classification task with minimal technical and computational effort." -- [Kaggle discussion](https://www.kaggle.com/discussions/questions-and-answers/715272)

### Inferences
- None of the retrieved sources were written about personal-scale, single-user projects specifically (all comparison studies used moderate-to-large labeled datasets typical of enterprise/research settings). Whether a single person can realistically accumulate "moderate amounts of training data" (the threshold at which fine-tuning wins) for their own idiosyncratic taxonomy within a reasonable time (weeks of usage, hundreds of corrections) is not directly addressed by any source -- this is the single most consequential inference gap for the target design decision.
- Given that a personal user's labeled set grows slowly (bounded by their own daily email volume and willingness to correct labels), and fine-tuning pipelines add real maintenance burden (retraining cadence, versioning, eval harness) for a solo developer, the balance of evidence leans toward "LLM zero/few-shot (or embeddings+kNN) is likely sufficient and lower-effort for a personal-scale project, with fine-tuning deferred as a later optimization once hundreds-to-thousands of corrected labels exist per category" -- this is the assistant's own reasoning synthesizing the above, not a direct claim from any source, and should be flagged as inference in the final report.

### Gaps
- No source directly discusses fine-tuning a small classifier on a single individual's email corpus (as opposed to enterprise-scale or benchmark-dataset studies). No practitioner blog post specifically weighing in on "is fine-tuning worth it for my own inbox" was found in this pass.
- No concrete numbers on how many labeled examples are needed for fine-tuning to start beating zero-shot in a classification setting resembling email triage (as opposed to the paper's four unspecified "applications").

## Hybrid cascade architectures (cheap rules -> small/cheap model -> large model)

### Takeaway
Cascade routing -- send every item to the cheapest tier first, escalate only on low confidence -- is a well-established and actively researched pattern in 2025-2026 LLM-serving literature, with a firm consensus that raw/self-reported model confidence is poorly calibrated and should not be trusted directly; instead, thresholds must be empirically calibrated against held-out labeled data for the specific workload. A concrete open-source personal email-triage project implements exactly this pattern with deterministic sender-based hard rules bypassing the LLM entirely at confidence 1.0.

### Cited Findings
- "Cascaded inference serves most requests with a small model and escalates hard cases to a large one, making it an attractive option for deployments where latency and serving cost matter." -- [Google Research: Speculative cascades -- A hybrid approach for smarter, faster LLM inference](https://research.google/blog/speculative-cascades-a-hybrid-approach-for-smarter-faster-llm-inference/)
- "Cascade routing sends every query to the cheap model first, checks whether the response meets a confidence threshold, and only escalates to the expensive model when it does not... Confidence thresholds can be swept from 0.01 to 0.99... Higher thresholds escalate more decisions, improving accuracy but increasing cost." -- [TianPan.co: LLM Routing and Model Cascades](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)
- "Empirically calibrated thresholds are non-negotiable. Any system that sets confidence thresholds by intuition will be miscalibrated. The correct approach is to evaluate your specific workload -- what fraction of queries the small model gets right at each confidence level -- and set thresholds based on your acceptable error rate." -- [TianPan.co](https://tianpan.co/blog/2025-11-03-llm-routing-model-cascades)
- "Cascade quality is bounded by the routing signal. LLM confidence scores, including raw token entropy and token margins, are typically miscalibrated, which creates implementation challenges for practitioners." -- [arXiv: Dynamic Model Routing and Cascading for Efficient LLM Inference: A Survey](https://arxiv.org/pdf/2603.04445)
- Concrete implementation: MailTriage/gmail-triage uses "a sender-pattern rule with no category" as a hard rule that "classifies deterministically with confidence 1.0 and bypasses the LLM entirely," runs its LLM tier as a local llama.cpp model at temperature 0 with JSON-schema enforcement (7-8B Qwen-class recommended floor), and separately tracks empirical per-category classification precision on a dashboard specifically because "LLM confidence is not calibrated" -- rule thresholds are tuned against these empirical counts, not against the LLM's self-reported score -- [GitHub: dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (via WebFetch summary)

### Inferences
- The gmail-triage example is a strong direct analog for the target project: rules tier (sender pattern / header heuristics) -> LLM tier (local or API model, structured output, temp 0) -> empirical-precision-driven threshold tuning, with no third "large model" escalation tier described in the retrieved summary -- for a personal project, a two-tier cascade (rules -> single LLM call) may be sufficient, and a three-tier cascade (rules -> cheap/fast LLM -> frontier LLM on genuine ambiguity) is an optional refinement rather than a necessity, since personal email volume is low enough that per-message LLM cost is not a major constraint even without a small-model tier.

### Gaps
- No source described a three-tier cascade (rules -> small model -> large model) specifically for email; the closest concrete example (gmail-triage) is a two-tier design (rules -> single local LLM). Whether adding a third "escalate to a frontier model when the local/small model is uncertain" tier is common in production email systems specifically was not confirmed by any source.
- No source gave concrete entropy or multi-model-disagreement formulas actually used in an email context (as opposed to general LLM-routing research).

## Confidence thresholds and abstention ("needs review" bucket)

### Takeaway
There is strong convergence across sources that self-reported/verbalized LLM confidence is not trustworthy for gating decisions; the recommended pattern is to calibrate a threshold (or a margin between top classes) against held-out, human-labeled evaluation data for the specific task and workload, treat human review capacity as a hard constraint on how aggressively to abstain, and -- when abstaining -- surface a clear explanation of what's uncertain rather than a bare "unclassified" bucket.

### Cited Findings
- "A fluent answer or a self-reported confidence score does not settle that question [of whether to accept an output]." Instead, the recommended approach uses held-out labeled evaluation data where reviewers assess outputs against a task-specific acceptance rubric -- confidence is treated operationally as "whether the proposed result passes a task-specific acceptance rubric," not as a number the model reports about itself -- [vdf.ai: When Should a Local Model Router Escalate or Abstain?](https://vdf.ai/blog/local-model-router-calibration-escalation-abstention/)
- Candidate routing signals suggested (evaluated/calibrated against outcomes, not used as raw preset thresholds) include "an independently evaluated task classifier, source coverage, extraction consistency, or a validation model's score" -- [vdf.ai](https://vdf.ai/blog/local-model-router-calibration-escalation-abstention/)
- "The system treats review capacity as a hard constraint," meaning abstention thresholds should reflect actual human review bandwidth, not just model uncertainty -- directly applicable to a personal tool, where "review capacity" is simply how many emails per day the user is willing to manually triage -- [vdf.ai](https://vdf.ai/blog/local-model-router-calibration-escalation-abstention/)
- On abstention, systems should provide "a useful explanation of what is missing and what the user or reviewer can do next," with the case entering a review queue -- [vdf.ai](https://vdf.ai/blog/local-model-router-calibration-escalation-abstention/)
- Independently, in a related abstention-literature framing: "Human review can be triggered when confidence scores fall below certain thresholds (e.g., c < 0.90) or when the margin between top class probabilities is below a threshold (e.g., delta < 0.10). Operating thresholds are often selected empirically during development to implement a conservative decision policy that prioritizes routing uncertain predictions to human review rather than maximizing automatic coverage." -- [search-aggregated summary of uncertainty-based abstention literature](https://openreview.net/pdf?id=1DIdt2YOPw)
- Consistent with the cascade-architecture findings above: MailTriage/gmail-triage explicitly does not trust LLM confidence and instead tracks empirical per-category precision to tune thresholds -- [GitHub: dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (via WebFetch summary)

### Inferences
- For a personal tool, "review capacity as a hard constraint" translates concretely to: size the "needs review" bucket to something the user will actually look at daily (e.g., no more than N emails/day), and tune the abstention threshold against that target rather than an abstract accuracy target -- this is the assistant's synthesis of the vdf.ai framing applied to the personal-scale context, not a directly sourced claim.
- A practical, low-effort proxy for "calibrated confidence" at personal scale: log every LLM classification alongside the user's eventual corrective action (if any), and periodically compute empirical precision per category (as gmail-triage does) rather than trying to build a proper calibration curve from token-level probabilities, which multiple sources say are unreliable anyway.

### Gaps
- No source described a concrete UX pattern for the "needs review" bucket itself (e.g., a special label, a digest email, an inbox view) -- this is more of a product-design question than a classification-technique question and may be better covered by a parallel research stream on products/UX.

## Taxonomy design: common personal email triage schemes

### Takeaway
Real products converge on a small set of recurring category shapes -- a "response-state" lifecycle (To Respond -> Awaiting Reply -> Actioned/Done, plus FYI and Marketing/Notifications as non-actionable buckets) is the most consistently observed pattern, distinct from Gmail's own fixed, mutually-exclusive, ML-classified tab categories (Primary/Social/Promotions/Updates/Forums). Best-practice guidance favors keeping categories mutually exclusive where possible, using a separate priority/urgency score layered on top of category rather than trying to encode urgency into the category set itself, and expects genuine overlap cases (e.g., a receipt that also needs a reply) to require an explicit tie-breaking rule.

### Cited Findings
- Fyxer AI's default taxonomy: "To Respond, FYI, Action, Comment, Notifications, Meeting Updates, Awaiting Reply, and Marketing" -- with defined semantics: "To Respond" = a message asking a question; "FYI" = informational, no reply needed; "Awaiting Reply" = state transition after the user replies to a "To Respond" item; "Marketing" = newsletters, promotional emails, cold outreach -- and a further "Actioned" state once a thread wraps up -- [Fyxer: How Fyxer organizes your inbox by priority](https://www.fyxer.com/blog/how-fyxer-organizes-your-inbox-by-priority); category list corroborated by [Jotform Blog: Fyxer AI vs Superhuman](https://www.jotform.com/ai/agents/fyxer-ai-vs-superhuman/)
- Fyxer's classification explicitly uses "content, context, sender history, and behavior patterns," and supports a manual-correction feedback loop: "if an email gets categorized incorrectly, you can move it manually and Fyxer will take that feedback into account and improve over time" -- [Fyxer blog](https://www.fyxer.com/blog/how-fyxer-organizes-your-inbox-by-priority)
- Superhuman, by contrast, does not impose a fixed AI taxonomy: it "provides a lighter layer of AI focused on drafting and polishing emails quickly, keeping the user in control," and "uses split inboxes... with more control over categorized emails because you create the categories [yourself]" -- i.e., Superhuman's approach is user-defined folders/split-inboxes rather than an automatically-applied fixed category set -- [Jotform Blog: Fyxer AI vs Superhuman](https://www.jotform.com/ai/agents/fyxer-ai-vs-superhuman/)
- Gmail's own built-in categories are described as "mutually exclusive, ML-classified, and cannot be customized," in explicit contrast to more flexible third-party category schemes -- [usecarly.com: How to Categorize Emails in Gmail](https://www.usecarly.com/blog/how-to-categorize-emails-in-gmail/)
- General best-practice guidance found in search results: "Categories should be kept mutually exclusive where possible, though overlapping categories like 'Billing' and 'Refund request' may require deciding whether refunds are a sub-category of billing or their own category" -- implying taxonomy designers should explicitly resolve overlap cases rather than leave them ambiguous. Note: this quote could not be traced to a single clearly-attributable primary article in the search results and should be treated as lower-confidence (see Gaps).
- A priority-scoring layer distinct from category: some described systems use "an overall importance ranking on how important the email is measured on a discrete scale from 1 (lowest) to 5 (highest)," and/or coarser buckets like "Act Now," "Read Promptly," "Act/Read Later," and "Other" -- implying urgency/priority is commonly treated as an orthogonal score or a small ordinal scale layered on top of a category label rather than folded into the category taxonomy itself -- [patent filing: Multi-tiered approach to E-mail prioritization](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9152953) (a patent document, not an engineering blog -- treat as weaker/indirect evidence of a design convention, not confirmed industry practice)
- A hands-on personal project used a flatter six-category taxonomy tuned for local-LLM feasibility: URGENT, ACTION_REQUIRED, INFORMATIONAL, SUSPICIOUS, PURCHASE, SHIPPING -- deliberately including "SUSPICIOUS" as its own bucket (distinct from Gmail's spam handling) and splitting commerce mail into PURCHASE vs. SHIPPING rather than lumping all transactional mail together -- [Zineb Bendhiba: I Tested Local LLMs to Triage My Gmail](https://zinebbendhiba.com/posts/i-tested-local-llms-to-triage-my-gmail-here-s-what-worked/)
- The MailTriage/gmail-triage project uses user-authored, plain-language category definitions rather than a fixed enum baked into code -- "categories: user-defined classifications with plain-language criteria; that text is the LLM prompt" -- meaning the taxonomy itself is a per-user configuration surface, not a hardcoded scheme -- [GitHub: dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage) (via WebFetch summary)

### Inferences
- Across the sources, there appear to be two fundamentally different taxonomy philosophies worth distinguishing explicitly for the design doc: (1) a fixed, response-lifecycle-oriented scheme (Fyxer-style: To Respond/Awaiting Reply/FYI/Marketing/Actioned) optimized for driving inbox-zero workflow, versus (2) a content/urgency-oriented scheme (the Zineb Bendhiba six-category example: URGENT/ACTION_REQUIRED/INFORMATIONAL/SUSPICIOUS/PURCHASE/SHIPPING) optimized for filtering and safety. A personal tool likely needs elements of both -- a response-state field (mutually exclusive, small) plus a content-type tag (which could be multi-label) plus a separate priority score -- rather than trying to cram everything into one flat category list. This is the assistant's own synthesis, not a claim any single source made.
- The "Eisenhower matrix" (urgent/important quadrants) and the specific "to respond / awaiting reply / FYI / done" framing "popularized by Superhuman and Front" mentioned in the task brief was not directly corroborated by the sources retrieved in this pass -- the retrieved evidence instead shows Fyxer (not Superhuman) as the product using that exact lifecycle taxonomy, and shows Superhuman explicitly not imposing a fixed AI taxonomy, preferring user-created split inboxes.
