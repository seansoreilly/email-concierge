# Feedback-Loop Mechanisms and Existing Products for LLM Email Triage

Research date: 2026-09-26. Compiled from three parallel research passes (Part A: feedback-loop design patterns; Part B1/B2: product survey). All claims are inline-cited; vendor marketing claims that could not be independently verified are explicitly flagged as such in place.

---

# Part A — Learning from Feedback in Personal LLM Email Triage Systems


## 1. Correction signals from relabeling/re-categorization

### Takeaway
In practice, personal-scale/indie tools close the feedback loop with one of three concrete mechanisms — (a) a human-reviewed "corrections log" that revises the natural-language classification criteria itself, (b) a traditional incremental ML classifier (e.g. scikit-learn `SGDClassifier`) retrained on accumulated human-confirmed labels, or (c) a raw few-shot corrections file appended to the prompt. None of the sourced examples do RLHF-style reward modeling — that only shows up in enterprise/academic literature, not personal tools.

### Cited Findings
- The **MailTriage** project (dmarchevsky/gmail-triage) lets a user "flag a misclassified email (correct category + optional note)"; the system then "proposes a criteria revision shown as a diff, consolidated with any other pending feedback for the same category," and the user can "approve / edit / reject from the Feedback page," with approval bumping "the category's criteria version (full history with restore)." Critically, "users write plain-language criteria; that text *is* the LLM prompt" — so a correction doesn't touch weights or a few-shot pool, it edits the natural-language rule text that is the classifier. — [dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage)
- The same project tracks "per-category empirical precision" on a dashboard because "LLM confidence is *not calibrated*," and tells users to "tune rule thresholds against these empirical counts" — i.e., corrections feed an observable metric that guides manual threshold/criteria tuning rather than an automatic model update. — [dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage)
- **InboxLearn** (sohaib-0897/InboxLearn) is an explicitly personal-scale, human-in-the-loop email classifier: "The system learns exclusively from human corrections," which are stored as "immutable feedback records" in SQLite. It does *not* do live online learning per-correction; instead a revision performs "a clean rebuild from seed plus latest corrections" — a full retrain of a `SGDClassifier(loss="log_loss")` over a `HashingVectorizer` feature space, with separate models for category and priority. — [sohaib-0897/InboxLearn](https://github.com/sohaib-0897/InboxLearn)
- InboxLearn treats model updates as a safety-gated release: "before/after prediction comparison and held-out evaluation are required before activation," candidate models stay as "inactive snapshots until explicitly approved," and rollback "restored the exact original predictions and confidence estimates on 15 probes" — i.e. corrections produce a *candidate* classifier version that must pass a regression check before replacing the live one. — [sohaib-0897/InboxLearn](https://github.com/sohaib-0897/InboxLearn)
- A published **Claude Code "Email Triage" skill** (listed on mcpmarket) stores misclassification feedback in a plain `corrections.md` file, described as "a corrections log for few-shot learning" — i.e. the correction becomes a literal few-shot example appended to what the LLM sees on the next classification pass, with acceptance criteria stating "Corrections from corrections.md reflected in classification." — [Email Triage Claude Code Skill](https://mcpmarket.com/tools/skills/email-triage)
- At enterprise/consumer scale, Gmail's own signal set for "Important" is explicitly a behavioral-feedback loop: it factors in "what emails you mark, star, archive, or delete; what you open and reply to... and which automatically marked emails you unmark" — i.e. every un-marking action is treated as a correction signal that adjusts future importance scoring. — [MakeUseOf: What Is Gmail's Importance Marker](https://www.makeuseof.com/what-is-gmail-importance-marker/)
- SaneBox's correction mechanism is pure behavioral relabeling: "drag emails between your Inbox and SaneBox folders... and the AI updates its model accordingly," with asymmetric latency — moves *into* the Inbox are noticed "almost immediately," while moves *out* of the Inbox take "5-15 minutes" to take effect — suggesting a deliberate bias toward fast-undo/false-positive correction over fast-suppress. — [SaneBox: How do I train/teach SaneBox?](https://www.sanebox.com/help/140-how-do-i-train-teach-sanebox)

### Inferences
- The three mechanisms above form a rough maturity ladder for a personal tool: (1) simplest — append the correction as a literal few-shot example to a prompt-level corrections file (mcpmarket skill); (2) mid — treat the correction as a vote that revises a natural-language *rule* which is itself the "model" (MailTriage); (3) most engineering-heavy — treat corrections as labeled training data for a small, separately-versioned statistical classifier with held-out evaluation gates before promotion (InboxLearn). For a first version of an email concierge, (1) is nearly free to implement and (2) gives the best interpretability/user-trust tradeoff, since the user can literally read the rule that changed.
- InboxLearn's "candidate model + held-out eval before activation" pattern is a good template for *any* correction mechanism, not just ML ones — even a prompt-text or few-shot-pool update could be gated behind a quick eval-set re-run (see Q4) before being treated as "live," which would catch a correction that overfits to one email and breaks classification of similar-but-distinct emails.
- None of the practical examples found do genuine RLHF (reward modeling + policy update) — this is very unlikely to be worth building at personal scale; the retrieval/rule/few-shot approaches above are simpler, cheaper, and directly interpretable to a single user, which matters more than raw sample efficiency.

### Gaps
- Could not find a documented example of an embeddings-based nearest-neighbor exemplar corpus (RAG-style retrieval of similar past-corrected examples) *specifically for email triage*. The closest analog found is academic work on RAG personalization for text generation (see Q1 general search), which discusses "within-user RAG" retrieval of a user's own past-labeled items, but no concrete email-triage implementation description surfaced — likely because indie/OSS email tools in this space are young (most repos found are from 2026) and haven't yet published this specific architecture.
- No confirmed example of "reinforcement-learning-from-feedback style" methods applied to personal-scale, non-enterprise email triage; this pattern appears to exist only in enterprise-scale importance ranking (Gmail) where it's implicit in continuous behavioral-signal ingestion, not an explicit RLHF pipeline.
- Update cadence (real-time vs. batch/nightly retrain) for the InboxLearn-style incremental classifier isn't fully specified beyond "clean rebuild... when revisions occur" — unclear if this is triggered per-correction or batched.

## 2. Per-sender memory

### Takeaway
Per-sender learning in shipped products is implemented as sender-keyed behavioral state (a "trained folder" per sender/domain in SaneBox, or an implicit reputation/interaction-history feature in Gmail's importance model) rather than as free-text natural-language rules; the mechanism is close to a lookup table of sender → learned disposition, updated by the same relabeling actions covered in Q1.

### Cited Findings
- SaneBox's core training primitive *is* per-sender: "the way you move emails...influences how SaneBox handles future emails from those senders," and the docs explicitly distinguish training scope — "Training for a whole Mailing List vs. an Individual Sender or Contact" is a separate configurable concept, meaning a user can choose whether a correction should generalize to a mailing list/domain or stay scoped to one address. — [SaneBox: Training for a whole Mailing List vs. an Individual Sender](https://www.sanebox.com/help/86-training-for-a-whole-mailing-list-vs-an-individual-sender-or-contact)
- For automated ("service") senders, SaneBox layers a second key on top of sender identity: it uses "both the sender and the email subject" so that, e.g., different email types from the same vendor (a newsletter vs. a shipping notification) can be trained into different folders independently — i.e. the per-sender memory is actually per-(sender, subject-pattern). — [SaneBox: How does SaneBox determine trainings?](https://www.sanebox.com/help/186-how-does-sanebox-determine-trainings)
- SaneBox explicitly does not read full email bodies for privacy reasons, relying only on "sender information and email subject lines" — meaning its per-sender model is intentionally a lightweight metadata classifier, not an LLM-driven content classifier. — [SaneBox: How does SaneBox determine trainings?](https://www.sanebox.com/help/186-how-does-sanebox-determine-trainings)
- Gmail's importance-ranking research describes signals keyed on the sender↔recipient relationship: "whom you email and how often, with frequent two-way contacts ranking higher," and per-sender interaction stats such as "the percentage of a sender's mail that is read by the recipient." This is per-sender *reputation* built from aggregate interaction statistics rather than an explicit user-authored rule. — [MakeUseOf: What Is Gmail's Importance Marker](https://www.makeuseof.com/what-is-gmail-importance-marker/)
- A generic "email agent" pattern described in a dev.to write-up implements per-sender rules as literal match conditions — "inbound rules can match on sender fields — `from.address`, `from.domain`, `from.tld` — with operators like `is`, `is_not`, `contains`, or `in_list`," feeding actions like `assign_to_folder`, `mark_as_read`, `archive` — and notes the routing table (an allow/deny-style list keyed on sender) can be edited by "non-engineers... with zero rule edits and zero deploys," implying the sender list is externalized as data, not baked into code/prompt. — [Folder Automation: Let Rules Sort the Agent's Mail](https://dev.to/qasim157/folder-automation-let-rules-sort-the-agents-mail-4o8i)

### Inferences
- The SaneBox "(sender, subject-pattern) → learned folder" model is a directly reusable design for a personal LLM concierge: maintain a small per-sender key-value store (last N dispositions, or a single "current disposition" enum) that is checked *before* invoking the LLM, so that repeat senders short-circuit to a cheap deterministic answer and the LLM is only invoked for novel senders — this also naturally reduces cost and latency versus re-classifying every email from a known sender with an LLM call.
- Gmail's per-sender reputation being built from aggregate stats (open rate, reply rate) rather than single explicit corrections suggests a hybrid design is stronger than either alone: blend an explicit "user moved this sender's mail" signal (strong, immediate) with an implicit behavioral signal (opened/replied/ignored, weak, gradual) so a sender's disposition can still drift correctly even without an explicit correction.
- The mailing-list-vs-individual-sender distinction (SaneBox) implies a personal tool should let a correction's *scope* be ambiguous-but-resolvable — i.e., ask (or infer from List-Unsubscribe / precedence headers) whether "always deprioritize this" should key on the exact From address or the whole domain/list.

### Gaps
- Could not find a primary source (Google paper, patent, or engineering blog) describing Gmail's per-sender feature update mechanism in implementation-level detail — the canonical paper ("The Learning Behind Gmail Priority Inbox," Aberdeen & Pacovsky, research.google.com/pubs/archive/36955.pdf) could not be extracted as readable text (PDF fetch returned corrupted/binary content); only secondary summaries (MakeUseOf, Mailmeteor) were usable, so Gmail claims here should be treated as vendor-adjacent secondary reporting, not verified from the primary paper.
- No OSS email-agent repo was found that documents an explicit numeric "sender reputation score" formula (decay rate, weighting of opens vs. replies vs. moves) — every source described the *existence* of per-sender learning but not the scoring math.

## 3. Natural-language preference rules

### Takeaway
The two shipped/OSS examples found land on opposite ends of the spectrum by design: MailTriage treats the user's plain-language criteria *as the literal LLM prompt* (pure prompt-injection, no compilation step), while a broader line of research ("Compile by Training") argues for compiling a natural-language spec into a reusable non-LLM program; most consumer products (Shortwave) are opaque about which end they're on, though their described behavior (persistent "AI Memories," saved one-click prompts) reads as prompt-injection with a memory layer rather than rule compilation.

### Cited Findings
- MailTriage is explicit and unambiguous about being an inference-time prompt-injection design: "users write plain-language criteria; that text *is* the LLM prompt" for a given category — there is no intermediate structured/compiled representation; the criteria text itself is versioned (with history and restore) as the unit of change. — [dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage)
- Shortwave documents a natural-language "AI filters" feature: "write simple instructions (in English) to label, mark, archive, highlight or prioritize emails using natural language filters, and the rules understand content context," plus a separate persistent-memory feature ("AI Memories") that lets users say things like "Remember I prefer short replies with emojis." The public docs do not disclose whether filters are compiled to a structured rule representation or re-interpreted by an LLM per email; this is described as proprietary/undisclosed. — [Shortwave: Customize your Shortwave](https://www.shortwave.com/docs/guides/customize-your-shortwave-settings/), [Shortwave AI Assistant docs](https://www.shortwave.com/docs/guides/ai-assistant/)
- A relevant *general* (non-email-specific) technique called "Compile by Training" proposes turning a natural-language specification into a "reusable program" that "can then be invoked repeatedly on new inputs without calling the teacher models again," explicitly contrasted with a system-prompt approach where "the language model interprets rules dynamically at runtime." The paper frames this as a performance/cost optimization: the compiled artifact "can be stored, versioned, cached, and reused like an ordinary software artifact" instead of paying an LLM inference cost (and incurring prompt-injection risk) on every classification. — [Compile by Training: Turning Natural-Language Specifications into Local Neural Functions (arXiv)](https://arxiv.org/pdf/2609.04199)
- A GitHub PR for an OSS "Hermes AI email triage agent" adds "natural language rule parsing for email triage" with structured `conditions` (from, to, subject, body, attachments, date, size) and `actions` (label, archive, forward, draft, notify, delete, move, star, markRead), plus "rule priority and enable/disable management" and "undo functionality" — the presence of discrete condition/action fields and 18 unit tests suggests natural-language input is parsed *into* a structured rule object rather than left as raw prompt text, though the PR description doesn't spell out the parsing implementation (LLM-based extraction vs. a grammar/regex parser). — [canatac/misfits-web PR #562](https://github.com/canatac/misfits-web/pull/562)

### Inferences
- The two ends of the spectrum map to different failure modes worth designing around: pure prompt-injection (MailTriage-style) is transparent and trivially editable by the user but re-pays LLM inference + prompt-injection risk on every email and its exact effect on classification is only empirically knowable (hence MailTriage's own emphasis on empirical-precision dashboards, see Q4); compiled/structured rules (Hermes-style, Compile-by-Training) are cheaper and deterministic at inference time but require a translation step that can silently misinterpret the user's freeform text, and are harder for the user to audit/edit directly.
- A practical middle ground implied by combining these sources: use the LLM to parse a natural-language preference into a structured, human-readable rule *object* (as Hermes appears to do) but keep the original natural-language sentence attached to that rule as its authoritative documentation/audit trail (as MailTriage's versioned-criteria-with-diff pattern does) — this gives the determinism/cost benefit of compilation while preserving the user-editability and transparency of plain text.
- Shortwave's split into "saved prompts" (one-off, invoked) vs. "AI Memories" (always-on persistent context) vs. "AI filters" (rule-like, per-email) suggests that in production, no single one of prompt-injection/compilation is used exclusively — different classes of preference ("always do X for sender Y" vs. "I generally prefer short replies") get routed to different mechanisms, which argues against forcing every kind of user preference through one representation.

### Gaps
- Could not confirm Shortwave's actual backend mechanism (prompt-injection vs. compiled rules vs. hybrid) from public documentation — this is explicitly proprietary/undisclosed, so any claim about their internals would be speculation.
- Could not find a primary technical write-up (blog, paper, or repo) from any product that explicitly and directly answers "prompt-injection vs. compilation" as a named design decision for *email* triage specifically — the clearest treatment of that exact tradeoff (Compile by Training) is a general-purpose NLP technique paper, not an email-specific one, so its applicability to email triage economics (call volume, latency tolerance) is my own inference, not a claim made in the source.
- Did not find user-reported failure cases (e.g. "the natural language rule did something I didn't mean") for any of these systems, which would help characterize real-world reliability of either approach.

## 4. Evals and golden sets for personal-scale classifiers

### Takeaway
The clearest working example found (Loukas998/email_triage) is a small, personal-scale, hand-labeled golden set (16 cases) checked into the repo as versioned JSON, run against versioned prompt YAML files with a lenient "exact / acceptable / missed" verdict scheme — a lightweight pattern well matched to a solo developer, though it uses synthetic/hand-written support-email cases rather than the user's own historical email as ground truth; general golden-dataset guidance (Langfuse) explicitly recommends sourcing from real production traffic and explicitly does not address personal email as a ground-truth source, leaving that specific idea unconfirmed by any source.

### Cited Findings
- **Loukas998/email_triage** (its own repo description: "Evaluating a change in the system prompt and how does it affect the model's response and testing it on a golden dataset") stores a golden dataset of "16 cases" of hand-labelled support emails at `golden/v1.json`, each with an expected category (billing/technical/account/general), "optional acceptable alternative categories," an expected summary, and a difficulty tag (easy/medium/hard). — [Loukas998/email_triage](https://github.com/Loukas998/email_triage)
- The same project versions prompts as YAML files under `prompts/` (model, temperature, thinking mode, system prompt) and runs `uv run python -m email_triage.check v1` to score every case with a verdict of exact match, "acceptable" (matches an alternative label), "missed," or validation error — explicitly enabling "prompt comparison (v1 vs v2) to measure how system prompt changes affect classification performance across difficulty tiers," and asserting as a gate that "no easy cases are missed." — [Loukas998/email_triage](https://github.com/Loukas998/email_triage)
- MailTriage's dashboard approach to evaluation is lighter-weight than a fixed golden set: rather than a static test file, it surfaces "per-category empirical precision" computed from the live corrections stream itself, with the explicit rationale that "LLM confidence is *not calibrated*" so raw model-reported confidence can't be trusted — this makes the corrections log double as an ad hoc, continuously-updated eval signal rather than a separate golden set. — [dmarchevsky/gmail-triage](https://github.com/dmarchevsky/gmail-triage)
- General (non-email-specific) golden-dataset guidance from Langfuse recommends starting from real traffic — "Real traffic beats invented examples, so start there" — capturing production failures into the dataset "while fresh," enforcing a JSON schema on entries, deduplicating near-identical items, and archiving (not deleting) obsolete cases; regression testing is done by "pinning a specific dataset version" and running each prompt/model variant against that same pinned version, automated in CI to "fail pull requests on regressions." Typical scale guidance elsewhere in this space is "20 to 50 reviewed items" as a minimum viable set, growing toward "100 to 1000" for a full regression suite. — [Langfuse: Golden dataset evaluation](https://langfuse.com/resources/engineering/golden-dataset-evaluation), [dev.to: Random Prompt Sampling vs. Golden Dataset](https://dev.to/practicaldeveloper/random-prompt-sampling-vs-golden-dataset-which-works-better-for-llm-regression-tests-1ln7)
- InboxLearn's "candidate model + held-out evaluation before activation" (see Q1) is functionally the same golden-set idea applied to a statistical classifier instead of an LLM prompt: a held-out slice of the user's own accumulated corrections acts as the personal golden set, and a new candidate must pass a before/after comparison against it before being promoted to the active model. — [sohaib-0897/InboxLearn](https://github.com/sohaib-0897/InboxLearn)

### Inferences
- Loukas998/email_triage's "exact / acceptable / missed" three-way verdict (rather than strict binary correctness) is a good template specifically for *personal* triage evals, where category boundaries are inherently fuzzy (a user might genuinely accept an email being filed as either "billing" or "account"); a strict-only golden set would likely produce noisy, hard-to-interpret regressions for a one-person classifier with idiosyncratic category definitions.
- Combining the MailTriage "corrections log as live empirical-precision signal" with the Loukas998/InboxLearn "static pinned golden set + gate" pattern gives a natural two-tier eval design for a personal concierge: a small (~20-50 item) golden set built from *the user's own* clearly-labeled historical decisions (archived-without-opening = low priority, starred = high priority, etc.) as the CI-style regression gate before shipping a prompt/model change, plus an always-on empirical-precision dashboard sourced from live corrections to catch drift *between* golden-set updates.
- None of the sourced examples actually build their golden set from a user's real historical inbox (starred/archived emails as ground truth) — every concrete example found uses hand-written or synthetic labeled emails. This specific idea (personal email history as golden-set source) is therefore currently an inference/design suggestion on my part, not something I can cite as an established practice, and should be flagged as a novel design choice to validate rather than assumed to work well (e.g., "archived" doesn't reliably mean "unimportant" — a user might archive something important right after reading it).

### Gaps
- Could not find any blog post, repo, or paper that explicitly and specifically describes building a personal email-classification golden set *from the user's own historical archive/star/read actions* — every real example found (Loukas998, Langfuse guidance, general golden-dataset write-ups) uses hand-labeled or production-trace-captured examples, not repurposed personal behavioral history as ground truth. This may simply not be a documented pattern yet, or my search terms didn't surface it — worth a follow-up search specifically for "inbox zero" / "email archive" combined with "eval set" or "ground truth," or checking newer (post-2026) Show HN posts directly.
- Could not verify how often personal-scale projects like Loukas998/email_triage or InboxLearn actually re-run their eval gate in practice (per-commit? per-prompt-edit? never, after initial setup?) — the repos describe the *mechanism* but not real usage cadence/frequency data.
- No cost/latency data found for running an LLM-as-judge or exact-match golden-set eval at personal scale (i.e., is it actually done on every prompt tweak, or only occasionally) — the enterprise-oriented sources (dataskew.io) frame this as CI-gated for teams, and it's unclear how much of that ceremony survives at solo-developer scale.

# Part B — Existing Products and Open-Source Projects Survey


## elie222/inbox-zero

### Takeaway
Inbox Zero is an open-source (self-hostable) "AI personal assistant for email" built around a natural-language "AI Rules" engine that converts plain-English instructions into automated actions (archive, label, draft, forward); it markets itself as always-on/live rather than digest-based, but neither the GitHub repo page nor its docs site publicly disclose the underlying LLM provider, exact OAuth scope strings, or any explicit learning/feedback loop.

### Cited Findings
- "Organizes your inbox and pre-drafts replies in your tone and style" — [GitHub - elie222/inbox-zero](https://github.com/elie222/inbox-zero)
- "AI Rules: Explain in plain English how your AI should handle your inbox" — [GitHub - elie222/inbox-zero](https://github.com/elie222/inbox-zero)
- Additional shipped features per the repo/marketing page: "Reply Zero" (tracks emails needing replies vs. awaiting response), "Bulk Unsubscriber," "Bulk Archiver," "Cold Email Blocker" (auto-blocks cold emails), "Email Analytics," meeting-prep briefings pulling from email+calendar, auto-filing attachments to Google Drive/OneDrive, and chat access via Slack/Telegram — [GitHub - elie222/inbox-zero](https://github.com/elie222/inbox-zero), [getinboxzero.com](https://www.getinboxzero.com/) (2026)
- On permissions, the docs describe scope *categories* rather than raw OAuth scope strings: Email access is described as needed to "read and organize messages and create drafts"; Calendar access "support[s] availability, booking links, and meeting features"; Drive access is for "filing attachments and attaching approved files to drafts" — [Security, Permissions, and AI — Inbox Zero Docs](https://docs.getinboxzero.com/essentials/security-and-data)
- The security docs mention a "sensitive-data policy" that "can allow, redact, or block detected credentials and payment-card numbers before content is sent to an AI provider" — implying user email content is sent off to a third-party LLM provider, but the provider is not named — [Security, Permissions, and AI — Inbox Zero Docs](https://docs.getinboxzero.com/essentials/security-and-data)
- Rules "run automatically after they are enabled," and users can review/correct behavior via an "Assistant → History" view and a "Fix" workflow when a rule misfires — [Security, Permissions, and AI — Inbox Zero Docs](https://docs.getinboxzero.com/essentials/security-and-data)
- Separately, there is a companion "inbox-zero" Claude Code Skill/CLI product (`getinboxzero.com/cli`, and a third-party `pearthefruit/inbox-zero` repo) described as "AI-powered email triage for Gmail" for agents; for that CLI variant, "the read-only scope lets the skill fetch and classify emails, and the write scope is required to create drafts and apply labels" — this describes the *agent-skill* variant's scope model, not necessarily the main hosted/self-hosted web app — [search result summary citing scope split](https://mcp.directory/skills/gmail-inbox-zero) (unverified primary source; flagged below)
- Inbox Zero states it has "CASA Tier 2 verification," a Google security-validation tier for apps requesting restricted Gmail scopes (vendor claim, not independently verified in this pass) — [search result](https://www.getinboxzero.com/blog/post/best-open-source-email-automation-tools-for-gmail)

### Inferences
- The "AI Rules" engine is almost certainly LLM-driven (natural-language rule authoring → structured automated actions) but the repo page content we fetched didn't surface implementation details (e.g., rule-matching per incoming email via LLM call vs. compiled conditions); given it's open source, the actual rule-matching code likely lives in the repo's source tree (not reachable via the GitHub landing-page fetch we did — a deeper repo/code search would be needed to confirm).
- The product is architected for **live intervention** (rules "run automatically," draft-pre-writing, auto-archive/auto-block) rather than a digest-only model — this is a design pattern distinct from Shortwave/Superhuman's more "bundle"-oriented default views.
- The "History"/"Fix" workflow suggests a manual correction UI exists, which is a proto-feedback-loop (user overrides a misfired rule), but there's no evidence this feedback is used to retrain/fine-tune anything — it more likely just adjusts the rule's future matching logic once corrected by the user, i.e., explicit rule-editing rather than implicit ML learning.

### Gaps
- No named LLM/model provider (OpenAI/Anthropic/etc.) found in any fetched page.
- No verified exact Gmail OAuth scope strings (e.g., whether it requests `gmail.modify` vs. full `mail.google.com`) for the main hosted app — only descriptive categories were found, and the one concrete "read-only vs. write scope" split found applies to the separate CLI/agent-skill product, not confirmed for the main web app.
- Did not fetch the actual source code (e.g., `apps/web` rule-matching logic) to confirm LLM-per-email calls vs. rule caching — repo README fetch returned marketing summary, not code-level detail.
- No confirmation of a digest/weekly-summary feature (analytics dashboard exists, but that's retrospective analytics, not a daily/weekly action digest).

### Inferences
- The three-bucket default taxonomy ("to respond" / "notification" / "fyi") is a much coarser categorization scheme than Shortwave's or Superhuman's (which support custom, prompt-defined labels) — Fyxer appears to optimize for a small, fixed decision surface rather than fully customizable rules.

## SaneBox

### Takeaway
SaneBox is a metadata-only, per-user-personalized filtering layer (not a full email client): it reads headers/sender/subject/behavior — never body content — and reclassifies mail into virtual IMAP folders (SaneLater, SaneBlackHole, SaneNews, etc.) with a daily digest of what got filtered. Its own docs stop short of naming the underlying algorithm (rules vs. statistical model), so the "how" is partially a black box even from primary sources.

### Cited Findings
- SaneLater automatically moves low-priority messages to a "SaneLater" folder, and a Daily Digest summarizes what was filtered so nothing is missed outright — [SaneBox Help: How does SaneBox work?](https://www.sanebox.com/help/155-how-does-sanebox-work)
- SaneBox explicitly does **not** analyze full email body content; classification is based on headers (sender, subject, etc.) and behavioral/interaction signals — [SaneBox Help: How does SaneBox work?](https://www.sanebox.com/help/155-how-does-sanebox-work)
- Training is per-user and explicit: dragging an email to/from a Sane folder retrains SaneBox for future mail from that sender; moving a message back to Inbox "retrains" it — [SaneBox Help: How do I train/teach SaneBox?](https://www.sanebox.com/help/140-how-do-i-train-teach-sanebox)
- Training can be scoped narrowly: the same sender's newsletter vs. shipping notification can be routed to different Sane folders based on *subject line* as well as sender, i.e. classification keys on (sender, subject) pairs, not sender alone — [SaneBox Help: How does SaneBox determine trainings?](https://www.sanebox.com/help/186-how-does-sanebox-determine-trainings)
- Moving/training a contact updates future routing for that sender going forward ("SaneBox will send future emails from that sender into the Sane folder the training was updated to") — [SaneBox Help: How does SaneBox determine trainings?](https://www.sanebox.com/help/186-how-does-sanebox-determine-trainings)

### Inferences
- The (sender, subject)-keyed training model plus "doesn't download the entire email body" strongly suggests a **statistical/heuristic classifier over metadata features** (sender reputation, header patterns, subject tokens, user interaction history) rather than a pure static rules engine — but SaneBox's own help docs never use the words "machine learning," "Bayesian," or "algorithm" with technical specificity, so this is inference, not a sourced claim.
- Personalization appears to be **per-user** (your own drag actions retrain your own account's filtering), not explicitly stated as pooling training signal across SaneBox's whole user base for a shared "sender reputation" score — though "sender reputation" language appears in marketing/review copy (see Gaps) which may hint at a cross-user component SaneBox doesn't document publicly.
- The digest pattern (SaneLater + Daily Digest) is a clean example of "asynchronous review, not live inbox intervention" — filtered mail isn't deleted or hidden, just moved and batched for a periodic human check.

### Gaps
- No SaneBox primary source (help docs or blog) technically confirms or denies use of ML/statistical models vs. deterministic rules — this is the single most-cited technical claim about SaneBox on the web but it traces back to secondary reviews/aggregators (e.g., GeeksforGeeks, AI Tool Radar, Volticen), not SaneBox engineering content. **Flagged as unverified vendor/reviewer claim.**
- No published information found on whether SaneBox pools "sender reputation" data across its whole user base (crowd-sourced spam/importance signal) vs. purely per-account learning. Third-party review sites assert "sender reputation" is used but don't cite a SaneBox source distinguishing per-user vs. aggregate.
- No architecture/technical blog post from SaneBox itself (e.g., engineering blog) was found describing the classifier internals — SaneBox appears to intentionally keep this proprietary.

## Other notable OSS email triage / agent projects

### Takeaway
Beyond SaneBox/Gmail, the OSS landscape splits cleanly into (a) one large, actively-maintained, GA-quality personal email assistant (Inbox Zero, ~9-12k GitHub stars) that does full LLM-based rule authoring + auto-drafting, and (b) a long tail of small/new projects (dozens of forks of Cloudflare's official template, single-star hobby repos) that mostly converge on the same safety pattern: **read-only access, rules-first/LLM-second triage, and drafts that are never auto-sent.**

### Cited Findings
- **Inbox Zero** (elie222/inbox-zero): open-source "AI personal assistant for email," ~9.3k stars / 1.1k forks per StackShare (a secondary source; GitHub page itself did not show a numeric star count in the fetched content but referenced ~12.3k and an actively maintained repo with continuous Docker builds on every push to `main`) — [GitHub: elie222/inbox-zero](https://github.com/elie222/inbox-zero), [StackShare comparison](https://stackshare.io/inbox-zero/vs/mailplane). Core pattern: "AI Rules" let the user explain in plain English how the AI should triage mail (LLM-based classification, not a static rules DSL), it pre-drafts replies "in your tone and style" (auto-draft, not auto-send), includes a "Cold Email Blocker" and "Bulk Unsubscriber," "Email Analytics," and integrates with Slack/Telegram so the assistant can be chatted with outside the inbox UI. No explicit OAuth-scope documentation was found in the fetched page.
- **Cloudflare Agentic Inbox** (cloudflare/agentic-inbox): official Cloudflare open-source (Apache 2.0) project — a full self-hosted email client (not just a triage layer) running entirely on Cloudflare Workers/Durable Objects/R2/Email Routing, with a built-in AI agent side panel exposing "9 email tools for reading, searching, drafting, and sending," built on Cloudflare's Agents SDK + Workers AI + AI SDK v6 — [GitHub: cloudflare/agentic-inbox](https://github.com/cloudflare/agentic-inbox). Notably, unlike most other projects surveyed, its agent tools reportedly include *sending*, not just drafting — a materially larger permission/action surface than Inbox Zero or inbox-agent.
- **inbox-agent** (AleBrito124356/inbox-agent): a small (2-star, single-commit) hobby project, but its documented design is a clean illustration of a conservative pattern worth borrowing regardless of its low adoption: a deterministic rules engine runs first (sender/subject/list-ID pattern matching, with a `skip_llm` flag) and only ambiguous mail is escalated to an LLM (NVIDIA NIM) for classification/action-item extraction — minimizing token spend. It generates a markdown daily digest (urgent / action-items / awaiting-reply-3-days+) rather than touching the inbox live, and drafts replies in the user's configured voice but explicitly **never sends**: "There is no SMTP code, no `send`, no API that transmits mail." IMAP access is read-only (`BODY.PEEK`, opened read-only) using scoped, revocable app passwords rather than the primary account password — [GitHub: AleBrito124356/inbox-agent](https://github.com/AleBrito124356/inbox-agent).

### Inferences
- Across all three OSS examples, "draft-only, human-sends" is the dominant safety convention for personal-scale tools — Cloudflare's Agentic Inbox is the outlier in exposing a send tool to the agent, which is a meaningfully different (higher-trust) permission model than Inbox Zero or inbox-agent.
- The rules-first/LLM-second architecture in inbox-agent (even though the repo itself is not widely used) mirrors a pattern worth adopting for cost/latency reasons: cheap deterministic filters triage the bulk of predictable mail (list IDs, known senders) and only route genuinely ambiguous messages to the LLM.
- None of the three surveyed OSS projects documented per-user learning/personalization beyond (a) Inbox Zero's natural-language "AI Rules" the user edits directly, and (b) inbox-agent's static `style.yaml` voice config — i.e., none of them described an adaptive/feedback-driven learning loop analogous to SaneBox's drag-to-train mechanism. Personalization in OSS tools so far looks like "user edits config/prompt," not "system learns from behavior."

### Gaps
- Star counts are inconsistent between sources for Inbox Zero (9.3k via StackShare vs. 12.3k referenced elsewhere) — likely reflects staleness in one of the two secondary sources; did not independently verify via GitHub API.
- No OAuth/Gmail-API scope documentation was found for Inbox Zero in the fetched content — worth checking its repo's source/docs directly (not just the landing README) if scope model matters for this project's design.
- Did not find 2-3 *other* actively-maintained (i.e., beyond Inbox Zero and Cloudflare's project) personal-scale OSS triage tools with substantial GitHub activity — the broader search surfaced many small/toy/single-star repos (AI-Email-Agent, Email-Assistant-Agents, open-email-agent) that were not independently vetted for star count or recent commit activity beyond what search snippets showed; treat these as long-tail/exploratory rather than proven patterns.
